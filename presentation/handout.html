Exercise

  • Ask the missing-information prompt. Classify each answer as supported, not found, or unsupported.

Expected solution

  • A good answer contains only claims justified by the provided text, short exact quotations, and clearly labeled limitations. A confident unsupported answer fails even if it is well written.

Prompts

Find one related paper record in the supplied CSV. Label it as a secondary summary and distinguish it from evidence in the PDF.
What was the exact cost of training the system, and does this paper prove it works for every domain? If the evidence does not say, write not found. Do not estimate.

03 · Responses: expose the loop

1:05–1:30 · 25 minutes

Outcome: Extract a typed result, then trace a bounded function-calling loop from request to final brief.

The model asks for a function; this Python line is what actually runs it.

Explain and show

  • Use notebooks/0.0-intro-responses-api.ipynb and notebooks/1.0-paper-data-extraction.ipynb. Begin with offline cells, then enable live calls only when prepared.
  • Structured output validates shape. A valid title, author list, or quotation field may still be wrong; compare extraction against the actual source.
  • ResponsesRuntime sends shared instructions, tool definitions, history, and a JSON schema. It preserves all returned output items before adding function-call results.
  • ToolBox.dispatch validates name and arguments, executes lookup_paper over the existing CSV or reads a PDF page, and returns a result. A matching call_id connects the result to the request.
  • A failed tool returns an explicit error and the brief must expose missing evidence. Step, tool-call, output-token, and wall-clock limits prevent an unbounded classroom loop.

Exercise

  • Open exercise.py. Implement matching_outputs so every model function call receives a JSON-encoded function_call_output with the original call_id.
  • Run solution.py locally. Predict the result of an unknown tool and a nonexistent CSV query before executing it.
  • Compare the ordinary and simulated-failure runs. Identify the missing evidence rather than treating an error-shaped result as a successful search.

Expected solution

  • See solution.py: dispatch each call by name and arguments, serialize the returned object, and preserve call_id. The model does not execute lookup_paper itself.
  • Unknown tool names return an explicit tool error; an ordinary unmatched search returns found=false and an empty record list. These outcomes have different meanings even if both leave the model without evidence.
  • Schema validation proves field/type conformity. Quote checks prove that a quoted substring exists in a known source. A person must still judge whether the claim follows from that quotation.

The SDK runs the loop inside our application; our application still owns its permissions and state strategy.

05 · Grounding & actions

1:55–2:15 · 20 minutes

Outcome: Distinguish file input from retrieval and enforce preview, explicit approval, authorization, and execute-once publication.

Evidence can inform the answer. It cannot grant itself permission to act.

Explain and show

  • The core app extracts a bounded set of PDF pages locally, then tools return evidence to the model. Direct PDF input is a different API pattern; file search adds retrieval over a collection.
  • The CSV is a collection of secondary summaries, not a web search or a vector store. Optional SEC retrieval uses local fixture search and is labeled as such.
  • Retrieved text may contain instructions. Treat it as untrusted evidence, never as authority to change tools, identity, policy, or output requirements.
  • The completed injection demo appends fixtures/injections/publish.txt to returned evidence and records the brief and tool results. Its offline default demonstrates the boundary deterministically; choose a verified live runtime explicitly to inspect actual model behavior.
  • The model's publish_brief function can only request approval. Actual mock publication requires an authenticated user, an exact preview digest, explicit approval, and publisher permission.
  • Publisher records approval and its local mock side effect in one SQLite transaction. Repeating an approved request reports already_published rather than repeating the side effect. No external publication occurs.

Exercise

  • Open exercise.py and complete the authorization decision table: approval absent, permission absent, wrong owner, changed digest, valid request, repeated valid request.
  • Run demo.py with its offline default to inspect hostile tool evidence, then choose --runtime responses, sdk, or managed only if that live path is prepared. Explain which application boundary prevents the retrieved instruction from publishing.
  • Choose direct PDF input or collection retrieval for one report versus 500 filings. State how source IDs and not-found behavior should survive either approach.

Expected solution

  • Missing approval, missing publisher permission, wrong owner, or changed content digest must deny. A valid request publishes once; repeating it returns already_published=true. solution.py exercises these cases against a temporary SQLite database.
  • Instructions inside returned evidence are data. The model may refuse or ignore them; the application permission boundary must still prevent publication even if the model follows them.
  • A small known paper can be passed or exposed directly. A collection usually benefits from retrieval; inspect retrieved passages and citations. Neither method establishes factual correctness merely by returning a source.

07 · Ship & recap

2:40–3:00 · 20 minutes

Outcome: Serve the same research task through an authenticated backend and Streamlit UI, then demonstrate the five exit requirements.

The interface can request work; the authenticated backend decides whose work it is and what may happen.

Explain and show

  • The Streamlit app sends requests to a separate authenticated FastAPI backend. The API key stays on the backend; a classroom bearer token identifies the user.
  • The backend isolates conversation ownership, serializes turns per session, caps work, expires idle sessions, and returns progress events plus a downloadable validated brief.
  • Start with offline mode for UI rehearsal. Live runtime selection sends the task and evidence to OpenAI; model access and costs still depend on the configured project.
  • This is a local classroom application: conversation state is in memory and mock publications are in SQLite. A public deployment needs TLS, production identity, durable shared state, job handling, and operational controls.
  • The optional ChatKit exercise replaces the archived workflow-ID integration with an adapter to your own authenticated backend. The existing Streamlit UI is the completed core deliverable.

Exercise

  • Run the app as one user, produce a brief, follow up, and download it. Start a second user's session and attempt to read the first session through the backend; expect denial.
  • Try publication without a publisher role, then preview and approve as an authorized user. Repeat the same approval and inspect idempotency.
  • Complete the five-part exit task. If live access is unavailable, record which elements were demonstrated only by offline rehearsal and list the remaining live checks.

Expected solution

  • Backend ownership checks return session not found to a different principal, even when that principal knows a session ID. Runtime state remains associated with its owning session.
  • Publication requires both the explicit approval flag and the server's can_publish role. The preview's digest binds approval to the exact brief; the SQLite transaction records one mock publication.
  • A complete exit packet includes the brief and its quotations, tool-call record, second-turn output, failure output, and ten-case results. A live model claim requires live metadata, not an offline transcript.
